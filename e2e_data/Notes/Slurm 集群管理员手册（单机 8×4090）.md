> **适用环境**  
> Ubuntu 22.04 | 单节点 Slurm | GPU 通过 GRES 管理 | 用户无 sudo | Cgroup v1

---

## 1. Slurm 核心组件与工作原理

你这台机器上的 Slurm 由三个关键部分构成：

**slurmctld**（调度器）负责接收用户的作业请求并决定资源分配，**slurmd**（执行器）在节点上创建 cgroup 并启动实际进程，**cgroup + /dev/nvidia***（资源隔离层）通过 Linux 内核机制真正限制 GPU/CPU/内存访问。任何"GPU 被乱用"的问题，最终都会落在 slurmd 和 cgroup 的配置上。

你的配置特点：

- `SelectType=select/cons_tres`：按 CPU 核心 + 内存 + GPU 精细分配
- `TaskPlugin=task/cgroup`：强制使用 cgroup 隔离
- `GresTypes=gpu`：GPU 作为通用资源管理
- `ConstrainDevices=yes`：这是 GPU 隔离的命门

## 2. 日常运维核心命令

### 2.1 第一反应：看状态

```bash
sinfo
```

节点状态解读：

- `idle`：正常空闲
- `alloc`：资源全部被占用
- `mix`：部分资源被占用
- `down`：节点失联（检查 slurmd）
- `drain`：手动或自动下线（必须处理）

---

### 2.2 谁在用资源

```bash
squeue
```

重点字段：`JOBID`、`USER`、`STATE`、`NODELIST`

查看 GPU 分配详情：

```bash
squeue -o "%.18i %.9P %.8j %.8u %.2t %.10M %.6D %R %b"
```

`%b` 列显示 GRES 分配（如 `gpu:2`）

按用户过滤：

```bash
squeue -u yuchengzhang
```

---

### 2.3 查看任务详情

```bash
scontrol show job 12345
```

关键信息：

- `JobState`：运行状态
- `Gres=gpu:2`：申请的 GPU 数量
- `CUDA_VISIBLE_DEVICES`：分配的 GPU 编号

---

### 2.4 节点详情

```bash
scontrol show node server-4090
```

关注：

- `State`：节点状态
- `Gres`：GPU 总数和可用数
- `Reason`：如果是 drain/down，这里会说明原因

## 3. 典型故障排查流程

### 3.1 用户反馈："申请了 GPU 但用不了"

按以下顺序排查，不要跳步：

**第 1 步：确认用户在 Slurm 作业内**

```bash
squeue -u username
```

如果没有任何输出，用户根本没提交作业或作业已结束。

**第 2 步：确认申请了 GPU**

```bash
scontrol show job <JOBID>
```

查找 `Gres=gpu:N`，如果没有这一行，用户的脚本没有 `--gres=gpu:N`。

**第 3 步：验证 cgroup 是否生效**

进入节点：

```bash
ps aux | grep <JOBID>
```

找到进程 PID，然后：

```bash
cat /proc/<PID>/cgroup
```

应该看到类似：

```text
12:devices:/slurm/uid_1000/job_12345
```

如果没有 `/slurm` 路径，说明 cgroup 配置失效。

**第 4 步：检查 GPU 设备权限**

在作业内执行：

```bash
ls -l /dev/nvidia*
```

如果权限被拒绝，检查 `/etc/slurm/cgroup.conf` 中 `ConstrainDevices=yes` 是否生效。

---

### 3.2 用户"偷偷裸跑 GPU"

**判断方法：**

1. `squeue` 没有该用户的作业
2. `nvidia-smi` 显示该用户有进程

这说明用户没通过 Slurm 直接运行了 GPU 程序。

**处理流程：**

立即终止进程：

```bash
sudo kill -9 <PID>
```

通知用户违规，必要时临时锁定账户：

```bash
sudo usermod -L username
```

**预防措施：**

启用 GPU 设备权限限制（仅允许 Slurm 作业访问）：

```bash
sudo groupadd slurm
sudo chown root:slurm /dev/nvidia*
sudo chmod 660 /dev/nvidia*
```

添加 udev 规则使重启后生效（`/etc/udev/rules.d/99-nvidia.rules`）：

```ini
KERNEL=="nvidia*", GROUP="slurm", MODE="0660"
```

重新加载：

```bash
sudo udevadm control --reload-rules
sudo udevadm trigger
```

---

### 3.3 节点变成 drain 状态

**原因排查：**

```bash
scontrol show node server-4090
```

查看 `Reason` 字段，常见原因：

- `Node unexpectedly rebooted`：系统重启但 Slurm 没收到通知
- `Not responding`：slurmd 挂了
- `Low tmp disk space`：`/var/spool/slurm` 空间不足

**恢复节点：**

修复根本问题后：

```bash
scontrol update NodeName=server-4090 State=RESUME
```

强制清除 drain 状态：

```bash
scontrol update NodeName=server-4090 State=IDLE
```

---

### 3.4 Slurm 服务起来了但不接任务

**快速排查：**

```bash
systemctl status slurmd
journalctl -u slurmd -n 50
```

**常见问题：**

1. **Munge 认证失败**

```bash
munge -n | unmunge
```

如果报错，重启 munge：

```bash
sudo systemctl restart munge
sudo systemctl restart slurmd
```

2. **权限问题**

```bash
sudo chown -R root:root /var/spool/slurm
sudo chmod 755 /var/spool/slurm
```

3. **配置文件语法错误**

```bash
sudo slurmd -C
```

会输出节点配置，如果有错误会直接报。

## 4. 配置文件管理原则

### 4.1 `/etc/slurm/slurm.conf`

**低风险可改：**

- `PartitionName`：分区名称和属性
- `MaxTime`：最大作业时长
- `Default=YES`：默认分区

**高风险慎改：**

- `SelectType`：资源选择算法（改了可能导致调度混乱）
- `TaskPlugin`：任务隔离插件（改了 cgroup 可能失效）
- `ProctrackType`：进程追踪方式（影响作业管理）
- `GresTypes`：通用资源类型（改了 GPU 调度失效）

**修改后必做：**

```bash
sudo systemctl restart slurmctld
sudo systemctl restart slurmd
```

---

### 4.2 `/etc/slurm/gres.conf`

这个文件只管一件事：GPU 编号映射。

```ini
Name=gpu File=/dev/nvidia[0-7]
```

**何时需要修改：**

- 新增或减少 GPU
- GPU 在 PCIe 总线上的顺序变化
- 更换硬件后 `/dev/nvidia*` 编号变化

**修改后重启：**

```bash
sudo systemctl restart slurmd
```

---

### 4.3 `/etc/slurm/cgroup.conf`

这是 GPU 隔离的生死线：

```ini
ConstrainDevices=yes
```

如果这一行是 `no` 或注释掉，Slurm 形同虚设，用户可以随意访问所有 GPU。

**其他重要参数：**

```ini
ConstrainCores=yes       # CPU 核心隔离
ConstrainRAMSpace=yes    # 内存限制
```

修改后必须重启 slurmd，且**不能在有作业运行时修改**。

---

## 5. 正确的重启流程

### 5.1 什么时候可以重启

安全时机：

- 所有作业已结束（`squeue` 为空）
- 实验环境，用户同意中断
- 紧急故障必须重启

**检查作业：**

```bash
squeue
```

如果有长时间运行的作业，联系用户协商。

---

### 5.2 标准重启顺序

```bash
sudo systemctl restart slurmctld
sleep 2
sudo systemctl restart slurmd
```

**为什么要这个顺序：** slurmd 启动时需要向 slurmctld 注册，如果 slurmctld 还没起来，slurmd 会注册失败。

---

### 5.3 危险操作（绝对禁止）

**在有作业运行时：**

- `kill -9 slurmd`：会导致作业变成僵尸进程
- 修改 `cgroup.conf`：会导致资源隔离失效
- 修改 `gres.conf`：会导致 GPU 分配错乱

**后果：**

- GPU 资源泄漏（作业结束但 GPU 还被占用）
- 作业卡死（进程在但 Slurm 不认识）
- 用户数据丢失

---

## 6. 用户管理实操

### 6.1 Slurm 与 Linux 用户的关系

Slurm 不管理用户权限，只识别 Linux 用户。只要 `id username` 存在，该用户就能提交作业。

**不要在 Slurm 里封禁用户**，在 Linux 层面处理：

```bash
sudo usermod -L username    # 锁定账户
sudo usermod -U username    # 解锁账户
```

---

### 6.2 临时禁止某用户使用

**方法 1：锁定登录**

```bash
sudo usermod -L username
```

**方法 2：移除主目录权限**

```bash
sudo chmod 000 /home/username
```

**方法 3：设置作业优先级为最低**

```bash
scontrol update PartitionName=debug PriorityTier=0
```

（需要 Slurm 多用户配置）

---

### 6.3 查看用户历史作业

```bash
sacct -u username --format=JobID,JobName,Partition,State,Elapsed,Start,End
```

筛选特定时间：

```bash
sacct -u username -S 2026-01-01 -E 2026-01-07
```

## 7. 日志排查指南

### 7.1 Slurm 服务日志

```bash
journalctl -u slurmctld -n 100 --no-pager
journalctl -u slurmd -n 100 --no-pager
```

关键字搜索：

```bash
journalctl -u slurmd | grep -i error
```

---

### 7.2 GPU 驱动问题

```bash
dmesg | grep -i nvidia
```

常见错误：

- `Xid 79`：GPU 挂了，需要重启或重置
- `NVRM`：驱动崩溃

---

### 7.3 Munge 认证问题

Munge 失败会导致所有 Slurm 操作失败。

测试：

```bash
munge -n | unmunge
```

正常输出：

```text
STATUS:           Success (0)
ENCODE_HOST:      server-4090
```

如果失败：

```bash
sudo systemctl restart munge
sudo systemctl restart slurmctld slurmd
```

## 8. 定期维护检查清单

**每周一次（5 分钟）：**

- - `sinfo` 确认节点状态正常
- - `squeue` 确认无僵尸作业（长时间 pending 或 completing）
- - `df -h /var/spool/slurm` 确认空间充足（>10GB）
- - `nvidia-smi` 确认无异常进程（不在 Slurm 作业内的进程）
- - `ls -l /dev/nvidia*` 确认权限正确（root:slurm 660）

**每月一次（10 分钟）：**

- - `journalctl -u slurmd --since "1 month ago" | grep -i error` 查看是否有反复出现的错误
- - `sacct -a -S $(date -d "1 month ago" +%Y-%m-%d)` 统计作业失败率
- - 清理 `/var/spool/slurm` 中的旧作业状态文件

## 9. 紧急情况处理手册

### 9.1 GPU 卡死（nvidia-smi 无响应）

```bash
sudo nvidia-smi -r -i 0  # 重置 GPU 0
```

如果重置失败，需要重启系统。

---

### 9.2 所有作业卡在 pending

**可能原因：**

1. 节点 drain 了：`scontrol update NodeName=server-4090 State=RESUME`
2. Slurmd 挂了：`sudo systemctl restart slurmd`
3. 资源全满：`squeue` 确认是否有其他作业占用

---

### 9.3 用户作业无法终止

```bash
scancel <JOBID>
```

如果无效，强制终止：

```bash
scancel -s KILL <JOBID>
```

如果还不行，找到进程 PID：

```bash
scontrol show job <JOBID> | grep RunTime
ps aux | grep <USERNAME>
sudo kill -9 <PID>
```

## 11. 一句话经验总结

管理 Slurm 的核心不是配置文件，而是理解"资源隔离靠 cgroup，问题排查看日志，用户违规从 Linux 层处理"。80% 的 GPU 问题来自用户没走 Slurm，不要为了"方便"牺牲 `ConstrainDevices=yes`，这是你唯一的安全保障。任何配置修改前先看 `squeue`，有作业就别动，重启永远先 slurmctld 后 slurmd，反过来会出事。
