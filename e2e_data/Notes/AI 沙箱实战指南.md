"每个 AI agent 最终都会提出同一个请求："

> 让我跑个程序。

有时候是无害的 `pytest`，有时候是 `pip install sketchy-package && python run.py`。不管是什么，一旦你让 agent 执行代码，你就是在一台你在乎的机器上运行不可信的字节。

多年前我做基础恶意软件分析时就学到了这个道理。当时的思维模型简单粗暴但很管用：**在一个你可以随时删掉的环境里运行恶意代码**。如果它逃出来了，直接核掉那个环境。

AI agent 重现了同样的问题，只不过现在的"恶意样本"往往是：

- 由模型生成的代码
- 用户粘贴进来的代码
- 或者 agent 自行拉取的依赖链——因为它"看起来对"

在所有这些场景中，代码都成了内核的客户端。它能获得内核和策略允许的一切：文件系统读取、网络访问、CPU 时间、内存、进程创建，有时甚至还有 GPU。

"逃逸"并非唯一的失败模式。即便没有内核漏洞利用，不可信代码也能：

- 窃取机密（SSH 密钥、云凭证、API 令牌）
- 把私有仓库代码外传
- 横向移动到内部网络
- 或者单纯烧你的钱（挖矿、fork 炸弹、失控的构建任务）

需求很简单：**运行这段程序，但别让它变成一个机器所有权问题。**

这已经不是小众话题了。[Vercel](https://vercel.com/sandbox)、[Cloudflare](https://developers.cloudflare.com/sandbox/) 和 [Google](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/agent-sandbox) 在过去一年都发布了沙箱执行产品。但底层的技术选型仍然被广泛误解，导致有些"沙箱"要么比预期更弱，要么比必要的更贵。

部分困惑源于 AI 执行有多种形态：

- **远程开发环境 / 编程 agent：** 长期存在的工作区，有 shell 访问权限、包管理器，有时还有 GPU。
- **无状态代码解释器：** 执行一段代码，返回输出，丢弃状态。
- **工具调用（Tool calling）：** 执行小型组件（如"读取这个文件""调用这个 API"），具有显式的能力授权。
- **RL 环境：** 大量并行运行，快速重置，有时支持快照/恢复。

不同的形态需要不同的生命周期和不同的边界。

这里面还隐藏着一个硬件演进的故事。2010 年时，"用虚拟机就行了"通常意味着几秒的启动时间和足以扼杀部署密度的开销。容器之所以胜出，是因为它们足够廉价。

到了 2026 年，你可以把 microVM 启动到感觉像容器一样快，还可以通过快照/恢复让"重置"几乎零成本。权衡空间变了，但我们的术语还没跟上。

另一部分困惑来自 **sandbox（沙箱）** 这个词本身。在实践中，人们用它指代至少四种不同的隔离边界：

**容器（Container）** 共享宿主内核。每次系统调用仍然落入运行其他所有东西的同一个内核。任何允许的系统调用路径中的内核 bug 就是宿主 bug。

**MicroVM** 在硬件虚拟化之后运行一个 guest 内核。工作负载与*它自己的*内核交互。宿主内核主要看到的是 KVM ioctl 和 virtio 设备 I/O，而不是完整的 Linux 系统调用 ABI。

**gVisor** 植入了一个用户空间内核。应用的系统调用由 Sentry 处理，而非直接进入宿主内核；Sentry 自身使用的宿主系统调用被限制在一个很小的白名单内。

**WebAssembly / Isolates** 将代码约束在一个运行时内部。没有环境文件系统或网络访问；guest 只能获得你显式提供的宿主能力。

这些隔离方式**不能互相替代**。它们有不同的启动成本、兼容性表现和失败模式。选错了，你要么会发布一个"会泄漏的沙箱"，要么得到一个无法运行你需要的软件的沙箱。

![四种沙箱边界的系统调用路径对比图](../access/sandboxes-for-ai/syscall-paths.webp)
*各种边界如何中介对宿主内核的访问。从左到右，直接的系统调用 ABI 暴露面逐渐缩小。*

这张图就是整个博弈的核心。容器暴露宿主内核的系统调用 ABI（经过策略过滤，但仍是同一个内核）。gVisor 插入了一个用户空间内核。MicroVM 在硬件虚拟化之后插入了一个 guest 内核。Wasm 模块根本不获得系统调用 ABI——它们只获得显式的宿主函数。

从左到右，直接系统调用 ABI 暴露面递减。

但天下没有免费的午餐。每一种"更强"的边界都引入了不同的可信组件：用户空间内核（gVisor）、guest 内核 + VMM（microVM），或运行时 + 宿主嵌入器（Wasm）。**更强不等于更简单，而是意味着你在押注不同的代码。**

如果这仍然让人觉得奇怪，那是因为这个行业训练我们把容器当成了默认答案。

回到 2010 年代中期。Docker 正在爆炸式增长。Kubernetes 让容器成为了调度的基本单元。虚拟机更重、启动更慢、运维更难。容器解决了一个真问题：快速启动、高密度部署、到处运行同一个构建产物。

对于*可信的*工作负载，这个赌注通常没问题：你本来就信任宿主内核。

AI agent 改变了威胁模型——因为你现在在你的基础设施中执行任意代码路径，这些代码通常由模型生成，有时由用户提供。

这并不意味着"永远不用容器"。而是意味着你需要一个比"用我们已有的东西"更清晰的决策流程。

在本文的其余部分，我将给你一个评估沙箱的简单心智模型，然后逐一介绍在真实 AI 执行系统中出现的各种隔离边界：容器、gVisor、microVM 和运行时沙箱。

## 三问模型

这是我使用的心智模型。沙箱设计本质上是三个独立的决策，但人们常常把它们混为一谈。区分清楚能避免很多错误判断。

**边界（Boundary）** 是隔离执行的位置。它定义了线的两边各有什么。

- 容器边界：进程在不同的命名空间中，但仍共享一个宿主内核。
- gVisor 边界：工作负载的系统调用先由用户空间内核（Sentry）处理。
- MicroVM 边界：系统调用进入 guest 内核；宿主内核看到的是 hypervisor/VMM 活动，而非 guest 的系统调用 ABI。
- 运行时边界：guest 代码没有系统调用 ABI；它只能调用显式的宿主 API。

边界就是你赌攻击者无法跨越的那条线。

**策略（Policy）** 是代码在边界内能触碰什么：

- 文件系统路径（读/写/执行）
- 网络目标和协议
- 进程创建/信号
- 设备访问（包括 GPU）
- 时间/内存/CPU/磁盘配额
- 接口暴露面本身（系统调用、ioctl、import）

在弱边界上配紧策略，仍然是弱沙箱。在强边界上配宽松策略，是浪费了机会。

**生命周期（Lifecycle）** 是两次运行之间什么会被保留。这对 agent 和 RL 非常重要：

- **全新运行（Fresh run）：** 什么都不保留。对恶意代码友好，但"agent 工作区"体验差。
- **工作区（Workspace）：** 长期存在的文件系统/会话。对 agent 友好；但如果机密泄露或持久化被滥用就很危险。
- **快照/恢复（Snapshot/restore）：** 通过检查点 VM 或运行时状态实现快速重置。非常适合 RL rollout 和"预热"agent。

生命周期还会影响你的运维选择。如果你需要快照，就需要一个可快照的边界（microVM 或某些运行时）。如果你需要工作区，就需要持久存储和关于机密管理的策略。

### 三个问题

评估任何沙箱时，问：

- **什么是共享的** ——这段代码和宿主之间共享了什么？
- **代码能触碰什么** ——文件、网络、设备、系统调用？
- **什么能跨运行保留** ——两次执行之间什么会留下来？

如果你能回答这些问题，你就理解了你的沙箱。如果回答不了，你就是在猜。

举个具体例子让这个区分更清晰：

- **多租户编程 agent**
  - 边界：microVM（guest 内核）
  - 策略：允许工作区文件系统，禁止宿主挂载，出站白名单，禁止裸设备
  - 生命周期：快照基础镜像，每会话克隆，关闭时销毁

同一产品思路，不同约束：

- **工具调用**（如"格式化这段代码"）
  - 边界：Wasm 组件
  - 策略：预开放一个目录，默认禁止网络
  - 生命周期：每次调用全新

### 术语

> **沙箱（Sandbox）**：边界 + 策略 + 生命周期。
>
> **容器（Container）**：一种打包格式加上基于内核特性的进程隔离。一个内核，多个隔离视图。
>
> **虚拟机（Virtual Machine）**：在虚拟硬件上运行的 guest 操作系统内核。
>
> **MicroVM**：针对快速启动和小体积优化的最小化虚拟机。
>
> **运行时沙箱（Runtime Sandbox）**：由运行时（Wasm、V8 isolates）而非操作系统来执行隔离。

## Linux 基础构建块

在比较沙箱类型之前，有必要明确我们要沙箱*对抗*什么。一个进程就是一个内核客户端。

![Linux 系统调用剖析图](../access/sandboxes-for-ai/linux-syscall-anatomy.webp)

它运行在用户空间。当它需要做真正的事情——读文件、创建 socket、分配内存、生成进程——就发起一次系统调用。这个系统调用进入内核。内核代码以完整权限运行。

如果在任何可达的系统调用路径、文件系统代码、网络代码或 ioctl 处理器中存在 bug，就可能被本地提权利用。这就是"容器逃逸"故事的根源。

如果你想要一个直觉画面：进程是一段无特权代码，反复请求内核代为执行操作。你可以限制它允许问的问题，但你无法让内核停止拥有特权。

Linux 容器是由四个基础原语构成的策略三明治：

### Namespace（命名空间）

命名空间通过提供内核子系统的独立实例，给进程一个隔离的资源视图：

- **PID 命名空间**：隔离的进程树 / PID 编号
- **Mount 命名空间**：隔离的挂载表 / 文件系统视图
- **Network 命名空间**：隔离的网络栈（接口、路由、netfilter 状态）
- **IPC/UTS 命名空间**：System V IPC 隔离和主机名隔离
- **User 命名空间**：UID/GID 映射和*能力作用域*

用户命名空间值得特别提及。它们允许你将"容器内的 root"映射到宿主上的一个无特权 UID。这改变了特权的含义。无根容器在这里获得了真正的安全收益，因为容器内的意外 "root" 不会自动意味着"宿主上的 root"。

但它仍然是同一个内核边界。内核 bug 就是内核 bug。

### Capabilities（能力）

Linux 把 "root" 拆分为多个 capabilities（细粒度权限）。容器通常以精简的 capability 集合启动，但它们往往仍包含足够多的能力，如果你给错了就会出事。

臭名昭著的是 `CAP_SYS_ADMIN`。它管控着一大堆松散相关的特权操作，实际上经常能解锁危险的内核接口。这就是为什么你会听到人们说"`SYS_ADMIN` 是新的 root"。

在真实沙箱中，应将 capability 的授予视为你的攻击面预算的一部分。最简单的优化往往就是*移除*你不需要的 capabilities。

### Cgroups（控制组）

Cgroups 限制和记账资源使用：

- CPU 配额/份额和 CPU 亲和性集合
- 内存限制
- I/O 带宽 / IOPS 限流
- 最大进程数（缓解 fork 炸弹）

Cgroups 主要用于防止资源耗尽。它们并不能实质性地减少内核攻击面。

### Seccomp

Seccomp 是系统调用过滤机制。进程安装一个 BPF 程序，在系统调用入口处运行；它可以检查系统调用号（在许多配置中还可以检查参数）并决定处理方式：允许、拒绝、记录、陷入（trap）、终止或通知一个监管进程。

严格的 seccomp 配置会阻止那些扩大内核攻击面或使提权成为可能的系统调用（`ptrace`、`mount`、`kexec_load`、`bpf`、`perf_event_open`、`userfaultfd` 等），还会阻止那些难以安全沙箱化的遗留接口。

作为一个简化示例，一个"拒绝危险系统调用"的 seccomp 规则通常像这样：

```json
{
  "defaultAction": "SCMP_ACT_ALLOW",
  "syscalls": [
    { "names": ["bpf", "perf_event_open", "kexec_load"], "action": "SCMP_ACT_ERRNO" }
  ]
}
```

在真实沙箱中，你还会过滤参数（`clone3` 的 flags、`ioctl` 的请求号），并且使用白名单而非黑名单。

还有一个 seccomp 特性值得了解，因为它出现在沙箱设计中：**seccomp 用户通知**（`SECCOMP_RET_USER_NOTIF`）。内核可以*暂停*一个系统调用，并将其发送给一个监管进程来决策，而不是简单地允许或拒绝。这让你可以构建"代理系统调用"（例如，只有当路径匹配策略时才允许 `open()`，或者通过策略引擎代理网络连接）。

这很强大，但不是免费的：代理系统调用增加了延迟和复杂度，而你的代理进程本身也成为了可信计算基的一部分。

但底线不变：你*允许*的那些系统调用仍然在宿主内核中执行。

### 容器如何组合这些

一个"容器"就是一个普通进程，配置了一组内核策略加上一个根文件系统：

- 命名空间限定/虚拟化资源
- Capabilities 被精简
- Cgroups 限制资源使用
- Seccomp 在入口过滤系统调用
- 根文件系统提供容器的 `/` 视图（通常通过 overlayfs 分层）
- AppArmor/SELinux 可能施加额外策略

![Linux 沙箱构建块图](../access/sandboxes-for-ai/linux-building-blocks.webp)
*概念上：系统调用进入宿主内核。Seccomp 可以在分发前阻止它们。命名空间限定资源范围。Cgroups 执行配额。但它仍是同一个宿主内核。*

这是在共享内核边界内的基于策略的限制。你减少进程能看到的东西（命名空间），限制它能消耗的（cgroups），并限制它能调用的系统调用（seccomp）。你并没有插入更强的隔离边界。

那么为什么人们把容器当作安全边界？因为"隔离的"和"安全的"被混为一谈了，而且容器在运维上确实很方便。

但如果你是在选沙箱，边界比便利性更重要。

## 容器的失败场景

我想直说：**容器不是敌对代码的充分安全边界**。它们可以被加固，这很重要。但它们仍然共享宿主内核。

我见得最多的失败模式是配置错误和内核/运行时 bug——加上第三种在 AI 系统中出现的：**策略泄漏**。

### 配置错误导致的逃逸

许多容器逃逸是自己造成的。运行时提供了削弱隔离的方式，而人们用了。

**`--privileged`** 移除了大多数防护。它实际上把容器变成了"多几步操作的宿主 root"。如果你的沙箱需要特权模式，你就没有沙箱。

**Docker 套接字**（`/var/run/docker.sock`）是另一个经典。挂载它之后你就可以请求宿主 Docker 守护进程创建新的特权容器、挂载宿主文件系统等等。实际上，访问 Docker 套接字就等于获得了宿主 root 权限。

**敏感挂载和过宽的 capabilities** 是常见问题列表中的其余部分：

- 可写的 `/sys` 或 `/proc/sys`
- 宿主路径以可写方式绑定挂载
- 添加宽泛的 capabilities（尤其是 `CAP_SYS_ADMIN`）
- 加入宿主命名空间（`--pid=host`、`--net=host`）
- 暴露原始内核接口的设备直通

这些是可以治理的问题：你可以审计配置并禁止明显的坑。

### 内核和运行时 Bug

正确配置的容器仍然共享宿主内核。如果内核在任何允许的系统调用、文件系统路径、网络栈行为或 ioctl 中存在 bug，容器内的代码就可以触发它。

与容器相关的本地提权漏洞案例：

- **Dirty COW**（[CVE-2016-5195](https://nvd.nist.gov/vuln/detail/CVE-2016-5195)）：内存子系统中的 copy-on-write 竞争条件。
- **Dirty Pipe**（[CVE-2022-0847](https://www.docker.com/blog/vulnerability-alert-avoiding-dirty-pipe-cve-2022-0847-on-docker-engine-and-docker-desktop/)）：管道处理 bug，可覆写只读映射中的数据。
- **fs_context 溢出**（[CVE-2022-0185](https://nvd.nist.gov/vuln/detail/CVE-2022-0185)）：文件系统上下文解析 bug，在容器环境中被利用。

Seccomp 通过阻止系统调用来减少暴露面，但你允许的系统调用仍然是内核代码。Docker 默认的 seccomp 配置文件是一个偏向兼容性的白名单：它阻止了一些高风险调用，但仍允许数百个。

而且不只是内核。一个容器运行时 bug 也可能足够（例如，runC 覆写：[CVE-2019-5736](https://nvd.nist.gov/vuln/detail/CVE-2019-5736)）。

### 策略泄漏（AI 特有的）

很多"agent 沙箱"的失败并非内核逃逸，而是策略失败。

如果你的沙箱能读代码仓库并有出站网络访问，agent 就能泄漏仓库内容。如果它能读 `~/.aws` 或挂载宿主卷，就能泄漏凭证。如果它能访问内部服务，就能成为横向移动的工具。

这就是为什么 agent 的沙箱设计往往更多地关于**显式能力设计**，而非"可用的最强边界"。边界很重要，但策略才是你控制*爆炸半径*的手段——当模型做出愚蠢行为或恶意 prompt 引导它时。

两点实用说明：

- **Rootless/用户命名空间有帮助。** 它们减少了意外特权的损害。但它们不会消除内核 bug。
- **多租户改变一切。** 如果你在同一个内核上运行来自不同信任域的代码，你应该假设有人会试图触发内核 bug 和侧信道攻击。"但这只是构建代码"不再是安慰。

还有一个容器特有的陷阱：**`ioctl` 是一个巨大的攻击面。** 即使你阻止了危险的系统调用，许多真实的内核接口隐藏在文件描述符上的 `ioctl()` 后面（文件系统、设备、网络）。如果你直通设备（尤其是 GPU），你就把大量驱动代码路径暴露给了不可信输入。

这就是为什么许多看起来像容器的"AI 沙箱"最终悄悄地在底层添加了更强的边界之一：要么是 gVisor 来减少宿主系统调用，要么是 microVM 来在宿主前面放一个 guest 内核。

这些都不意味着容器"不好"。而是意味着当容器内所有代码都与宿主在同一信任域时，容器是一个优秀的工具。如果你运行自己的服务，这通常成立。

一旦你接受了来自信任边界之外的代码（用户、agent、插件），就应该把"共享内核"视为一个有意识的风险决策——而非默认选项。

### 加固选项

加固收紧的是策略，而非改变边界。

| 加固措施 | 作用 | 不能解决什么 |
|---------|------|------------|
| **自定义 seccomp** | 比默认阻止更多系统调用/参数 | 不能防御允许路径中的内核 bug |
| **AppArmor/SELinux** | 约束文件系统/procfs 和敏感操作 | 不能修复内核 bug；只减少可达路径 |
| **丢弃 capabilities** | 移除特权接口（避免 `SYS_ADMIN`） | 不改变共享内核边界 |
| **只读 rootfs** | 防止对容器根的写入 | 不能防止内存中/内核级的利用 |
| **用户命名空间** | 将容器 root 映射到无特权宿主 UID | 内核 bug 仍可能允许提权 |

在极限情况下，你可以把容器加固到几乎不可用。但你仍然没有改变边界。你允许的那几个系统调用仍然是特权内核代码。内核仍然是共享的。

如果内核漏洞利用是你关心的，你需要不同的边界：

- gVisor：系统调用拦截
- MicroVM：虚拟化之后的 guest 内核
- Wasm/Isolates：根本没有系统调用 ABI

## 更强的边界

容器有一个根本约束：工作负载的系统调用进入宿主内核。要真正改变边界，有两种主要方法：

- **系统调用拦截（Syscall interposition）：** 在系统调用到达宿主内核之前拦截它们，在用户空间重新实现足够多的 Linux
- **硬件虚拟化：** 在 VMM/hypervisor 之后运行一个 guest 内核，将宿主暴露面缩减为 VM exit 和设备 I/O

### gVisor

[gVisor](https://gvisor.dev/docs/) 是一个"应用内核"，拦截来自容器的系统调用（和一些 fault），并在一个叫做 **Sentry** 的用户空间内核中处理它们。

如果说容器是"命名空间中的进程"，那 gVisor 就是"命名空间中的进程，但它们的系统调用不直接进入宿主内核"。

选择它时有几个实现细节需要注意：

- gVisor 作为 OCI 运行时（`runsc`）集成，因此可以直接嵌入 Docker/Kubernetes。
- Sentry 用 Go 实现内核逻辑：系统调用、信号、部分 `/proc`、网络栈等。
- 拦截通过 gVisor 的 **platform** 完成。目前默认是 **systrap**；较老的部署使用 **ptrace**，还有可选的 **KVM** 模式。

有两个子系统值得深入了解，因为它们主导了性能和安全行为：

**文件系统中介（Gofer / lisafs）。** gVisor 通常拆分职责：Sentry 执行系统调用语义，但文件系统访问可能由一个独立组件中介，该组件执行宿主文件系统操作并通过协议服务给 Sentry（历史上叫"Gofer"；更新的工作包括 lisafs）。这是 gVisor 保持 Sentry 宿主接口小且可审计的方式之一。

**网络（netstack vs host）。** gVisor 可以使用自己的用户空间网络栈（"netstack"），避免像容器那样与宿主网络栈交互。也有更直接集成宿主网络的模式，取决于部署约束。

安全关键点在于：工作负载不再选择调用哪些宿主系统调用。Sentry 来决定，而 Sentry 自身可以被约束在一个小的宿主系统调用白名单内。gVisor 公布过系统调用白名单数字：在一种配置中，**无网络时 53 个宿主系统调用，加上网络后再加 15 个**（共 68 个），通过 seccomp 在 Sentry 进程上强制执行。

那和"你的容器工作负载能发起的任何系统调用"是完全不同的接口。

权衡是可预期的：

- **兼容性：** 并非每个系统调用和内核行为都完全一致。有一个[系统调用兼容性表](https://gvisor.dev/docs/user_guide/compatibility/linux/amd64/)，你终究会碰到它。
- **开销：** 系统调用拦截不是免费的。系统调用密集的工作负载付出更多。文件系统密集的工作负载要为中介和额外的拷贝/IPC 付费。
- **可调试性：** 失败模式包括未实现调用返回 `ENOSYS`，或微妙的语义不匹配。

我的看法：gVisor 最适合你能容忍"Linux，但有兼容性矩阵"，并且你想要比标准容器小得多的宿主内核接口的场景。

![gVisor 架构图](../access/sandboxes-for-ai/gvisor.webp)

### MicroVM

系统调用拦截的替代方案是硬件隔离。在硬件虚拟化（Linux 上的 KVM，macOS 上的 Hypervisor.framework）之后运行一个 guest 内核。宿主内核看到的是 VM exit 和 virtio 设备 I/O，而非各个工作负载的系统调用。

这就是为什么 microVM 是"为陌生人运行任意 Linux 代码"的默认答案。你获得完整的 Linux 语义，而无需重新实现系统调用 ABI。

#### 宿主内核实际看到什么

MicroVM 仍然使用宿主内核，但接口的形态变了：

- VMM 通过 `/dev/kvm` ioctl 创建 vCPU、映射 guest 内存并运行 VM。
- Guest 与虚拟设备（virtio-net、virtio-blk、vsock）交互。这些设备由 VMM（或 vhost-user 等后端）实现。
- 执行过程在特权事件、设备 I/O、中断等时触发 VM exit（陷入宿主）。

宿主内核仍然中介访问，但通过一个比完整 Linux 系统调用 ABI 更窄、更结构化的接口。

#### MicroVM 本身不解决什么

Guest 内核边界不自动意味着"安全"。

你仍然需要决定策略：

- Guest 有出站网络访问吗？
- 它挂载了机密或凭证吗？
- 它能访问内部服务吗？
- 它在不同运行之间共享文件系统状态吗？

MicroVM 是一个强*边界*，但你仍然需要强*策略*来防止它变成一个高性能数据外泄工具。

大规模部署中，基于 microVM 的沙箱收敛到几种生命周期模式：

- **临时会话 VM：** 启动 → 运行命令 → 销毁。简单可靠。
- **快照克隆：** 启动一次"黄金"VM（语言运行时、包缓存）→ 快照 → 每会话克隆。冷启动快，重置也快。
- **Fork-and-exec 风格：** 保持一个暂停/挂起 VM 的池，按需恢复。运维更复杂但可以减少尾延迟。

状态注入也是一个设计选择，而非给定的：

- **块设备镜像**（virtio-blk 内的 ext4）：简单、可移植、对快照友好。
- **virtio-fs / 9p 类共享：** 将宿主目录共享到 guest（对"工作区镜像"有用，但重新引入了宿主文件系统作为策略面的一部分）。
- **网络拉取：** 从对象存储/Git remote 将代码拉入 guest。将宿主文件系统排除在 guest 边界之外，但需要网络策略。

你还需要一个网络方案。常见模式：

- **NAT + 出站白名单：** SaaS agent 最常用。
- **无直接互联网：** 强制所有流量经过执行策略和日志的代理。
- **专用 VPC/子网：** 将"不可信执行"隔离在远离内部服务的地方。

最后，如果你关心的是*保护 guest 不被宿主窥探*（例如"用户不信任运营商"），可以关注机密计算（SEV-SNP/TDX）和 Confidential Containers 等项目。那是不同的威胁模型，但对托管 agent 执行越来越重要。

![容器 vs microVM 对比图](../access/sandboxes-for-ai/container-vs-microvm.webp)

#### 什么是 VMM？

在 Linux 上，"VM"分两层：

- **KVM**（在内核中）：把 Linux 变成 hypervisor，通过 `/dev/kvm` ioctl 暴露虚拟化原语。
- **VMM**（用户空间）：分配 guest 内存，配置 vCPU，提供 guest 使用的虚拟设备。

QEMU 是经典的通用 VMM：大量设备、大量遗留路径、大量代码。这种灵活性有用——但也是攻击面和运维成本。

MicroVM 的 VMM 有意精简：更少设备、更少模拟路径、更小体积、更快启动。

#### 设备模型是新的接口

从"容器系统调用"转到"microVM"是在转移攻击面，而非消除它。

你不再担心宿主内核中的每个系统调用处理器，转而担心：

- 宿主内核中的 KVM ioctl 处理
- VMM 进程（它对设备配置的解析、事件循环）
- **虚拟设备实现**（virtio-net、virtio-blk、virtio-fs、vsock）

这就是为什么 microVM 的 VMM 对最小化设备非常激进。每增加一个设备就意味着更多解析、更多状态机、更多边缘情况。

它还改变了你的补丁责任。有了 microVM，你现在有*两个*内核需要保持健康：

- **宿主内核**（KVM 和相关子系统）
- **guest 内核**（你的不可信代码实际首先攻击的）

Guest 内核可以比通用发行版内核更精简：禁用不需要的模块，移除不挂载的文件系统，避免冷门驱动。这不能替代打补丁，但可以缩小可达代码。

#### Virtio，但哪种口味？

Virtio 设备可以通过不同的传输层暴露。Firecracker 使用 **virtio-mmio**（简单、最小），其他 VMM 常用 **virtio-pci**（更像"普通 VM"，更广的设备生态）。通常你不在乎——直到你在乎的那天：某些 guest 工具假定 PCI，某些性能特性假定特定栈，直通工作倾向于以 PCI 为中心。

"MicroVM"描述的是一种设计立场：移除遗留设备，保持设备模型小。

#### Firecracker

[Firecracker](https://github.com/firecracker-microvm/firecracker) 是 AWS 为多租户无服务器（Lambda、Fargate）打造的极简 VMM。它专门为运行大量小 VM 并严格限制宿主而设计。

架构故意做得很无聊：

- 每个 microVM 一个 Firecracker 进程
- 最小 virtio 设备模型（net、block、vsock、console）
- 一个"jailer"在 guest 运行前为 VMM 进程设置隔离

内部可以理解为三种线程类型：

- API 线程（控制面）
- VMM 线程（设备模型和 I/O）
- vCPU 线程（运行 KVM 循环）

安全策略是围绕 VMM 的纵深防御：

- Jailer 设置 chroot + 命名空间 + cgroups，放弃特权，然后 exec VMM。
- 严格的 seccomp 配置约束 VMM。Firecracker NSDI 论文描述了 **24 个系统调用**（带参数过滤）和 **30 个 ioctl** 的白名单。

Firecracker microVM 通过一个小的 API（REST API 或 socket）配置。典型的"远程开发环境"产品在这个 API 之上构建更高级的生命周期管理：启动、快照、恢复、暂停、恢复、收集日志。

示例：VMM 不会"挂载你的仓库"。你来决定如何注入状态：附加块设备、挂载 virtio-fs 共享，或者在 guest 内通过网络拉取代码。这些选择都是策略选择。

快照/恢复对 agent 和 RL 是实际的优势：

- **Agent：** 你可以预热一个基础镜像（语言运行时、包缓存）并快速克隆。
- **RL：** 你可以重置到已知状态而无需重放漫长的初始化序列。

Firecracker 支持快照，但快照性能和正确性取决于工作负载（内存大小、设备状态、熵源）。把它当作"在很多场景下工作良好"，而非"免费的"。

几个实际限制要记住：

- Firecracker 专注于现代 Linux guest。它有意避免大量"PC 兼容性"硬件。
- 设备集合设计上就是最小的。如果你的工作负载依赖冷门设备或内核模块，你需要适配 guest 或选择其他 VMM。
- 调试更像"调试一个微型 VM"而非"调试一个容器"。你需要好的串口控制台日志和 VMM 的监控指标。

还有一个重要的细微差别："125ms 启动"通常指的是 VMM 和 guest 的启动路径。如果你通过更重的控制面（containerd、网络设置、存储编排）启动 Firecracker，端到端冷启动可能更高。在你的栈中实际测量。

![Firecracker 架构图](../access/sandboxes-for-ai/firecracker.webp)

#### cloud-hypervisor

[cloud-hypervisor](https://www.cloudhypervisor.org/) 也是一个 Rust VMM，基于同一个 rust-vmm 生态构建，但面向更广泛的"现代云 VM"用例。

与 Firecracker 的差异在于功能和设备模型：

- 基于 PCI 的 virtio 设备（非 virtio-mmio）
- CPU/内存/设备热插拔
- 可选的 vhost-user 后端（将设备后端移出进程）
- **VFIO 直通**（包括 GPU，受限于通常的 IOMMU/VFIO 约束）
- Windows guest 支持

如果你需要"VM 边界*加上* GPU 直通"，这是常见的落脚点。该项目声称使用直接内核引导可以在 100ms 内启动到用户空间。

关于 GPU 直通的注意事项：VFIO 给了 guest 对硬件更多的直接访问。这可能是必要的且仍然安全，但它改变了失败模式。你现在需要关心设备固件、IOMMU 隔离和 hypervisor 配置——这些在"仅 CPU 的 microVM"设计中不需要关心。许多系统选择混合方案：通用代码执行用仅 CPU 的 microVM，模型执行用独立的 GPU 服务边界。

#### libkrun

[libkrun](https://github.com/containers/libkrun) 采用不同方法：它是一个嵌入为库的最小 VMM，提供 C API。在 Linux 上使用 KVM，在 macOS/ARM64 上使用 Hypervisor.framework。

这出现在"在笔记本上用轻量级 VM 运行容器"的工具中，它之所以相关是因为本地 agent 越来越成为一流工作流。libkrun 还有一个有趣的 macOS 角度：virtio-gpu + Mesa Venus 在 Apple Silicon 上转发 Vulkan 调用（Vulkan→MoltenVK→Metal）。在许多配置中，这就是一些容器栈如何在 macOS 上获得 GPU 加速而无需"全脂"VM 管理器的方式。

注意点是信任边界可能不同。使用嵌入式 VMM 时，你需要将 VMM 进程本身视为你的 TCB 的一部分，并像任何其他特权辅助程序一样对其进行沙箱化。

### MicroVM 选项速览

| VMM | 最擅长 | 不太擅长 |
|-----|--------|---------|
| Firecracker | 多租户密度、严格宿主限制、快照 | 通用 VM 功能、GPU 直通 |
| cloud-hypervisor | 更广的 VM 功能集；VFIO/热插拔；Windows 支持 | 最小可能的攻击面 |
| libkrun | 开发机上的轻量 VM（尤其是 macOS/ARM64） | 大规模多租户控制面 |

### gVisor vs MicroVM

如果你在"系统调用拦截"和"硬件虚拟化"之间做选择，实际的权衡是：

- **兼容性：** microVM 是完整 Linux；gVisor 是"大部分 Linux"，你需要验证。
- **开销：** gVisor 避免运行 guest 内核；microVM 要为 guest 内核和 VMM 付费（但仍然可以很快）。
- **攻击面：** gVisor 押注用户空间内核实现和小的宿主系统调用白名单；microVM 押注 KVM + VMM 设备面。

没有绝对的赢家。威胁模型和工作负载特征通常决定选择。

### Kata Containers

Kata 解决了一个常见的运维约束："我想保留容器工作流，但需要 VM 级别的隔离。"

[Kata Containers](https://katacontainers.io/) 是一个 OCI 兼容的运行时，在一个轻量级沙箱 VM 中运行容器（通常在 Kubernetes 中是 pod 级别：一个 pod 中的多个容器共享一个 VM）。

架构概括为一段话：

- containerd/CRI 使用 Kata 运行时 shim 创建 pod 沙箱
- shim 使用配置的 hypervisor 后端（QEMU、Firecracker、cloud-hypervisor 等）启动轻量 VM
- VM 内的 `kata-agent` 启动和管理容器进程
- 根文件系统通过 virtio-fs 共享到 guest
- 网络和 vsock 通过 virtio 设备提供

吸引力在于**容器的开发体验加上 guest 内核边界**。成本是开销：每个沙箱 VM 都带一个 guest 内核加 VMM/设备中介，启动也增加延迟。

Kata 在你在同一个 Kubernetes 集群上运行混合信任工作负载、想要 VM 边界而又不想重写平台时很有意义。

运维上，Kata 通常通过 Kubernetes 的 `RuntimeClass` 引入：一些 pod 使用默认的 runc 容器运行时；不可信 pod 使用 Kata 运行时类。这让你无需另建集群就能混合可信和不可信工作负载。

如果你在探索机密计算，Kata 也是 Confidential Containers（SEV-SNP/TDX 等硬件支持的隔离）的常见集成点。这对"沙箱化敌对代码"不是必需的，但如果你需要租户隔离*并且*需要对基础设施运营商的更强保证，它就很相关了。

## 运行时沙箱

现在来看一些真正不同的东西。容器、gVisor 和 microVM 都是以"进程"形式运行代码，guest 看到的仍是某种系统调用 ABI（宿主内核、用户空间内核或 guest 内核）。

运行时沙箱翻转了这个模型。隔离边界存在于运行时内部。被沙箱化的代码永远不会获得宿主的系统调用 ABI。它只能获得运行时（和宿主嵌入器）显式提供的东西。

![运行时沙箱边界图](../access/sandboxes-for-ai/runtime-sandbox.webp)

### WebAssembly

WebAssembly 是一个字节码沙箱，具有清晰的能力（capability）模型。模块无法触碰外部世界，除非宿主暴露了 import。

这和"给你一个 POSIX 进程，请自觉"是根本不同的默认设定。

Wasm 运行时强制执行：

- **内存隔离：** 模块在线性内存中操作；越界读写会触发陷阱。
- **受约束的控制流：** 不能任意跳转到原始地址。
- **无环境 OS 访问：** 宿主调用是显式的 import。

WASI（WebAssembly System Interface）用面向能力的 API 扩展了这一点。标志性设计是**预开放目录（preopened directories）**：不是让模块打开任意路径，而是给它一个目录句柄代表"这棵子树"，它只能在里面解析相对路径。

实践中的感觉（伪代码）：

```javascript
// 给模块一个 ./workspace 的视图，而非宿主文件系统。
wasi.preopenDir("./workspace", "/work");
// 允许向特定主机发出 HTTPS 请求。
wasi.allowNet(["api.github.com:443"]);
```

如果你从不预开放 `~/.ssh`，模块就无法读取它。不存在"你的应用中忘记检查路径前缀的 bug 意外授予了访问权限"，因为能力从未被授予。

性能通常很出色，因为没有 guest OS 需要启动。实例/模块实例化可以是微秒到毫秒级，取决于运行时和编译模式（AOT vs JIT）。这就是为什么边缘平台喜欢 Wasm 和 isolates：高密度、低冷启动。

一个在真实沙箱中很重要的细节：**资源计量**。运行时沙箱不会魔法般地阻止无限循环或指数级算法。你仍然需要 CPU/时间限制。许多运行时提供"fuel"或指令计量（如 Wasmtime 的 fuel），让你可以确定性地抢占失控执行。

局限性通常表现为"我需要再多一个宿主函数"：

- 真正的安全边界是你的 **import 面**。如果你暴露了一个强大的 `runCommand()` 宿主调用，你等于重新发明了 shell。
- 保持 import 窄且有类型。优先选择结构化操作（"从预开放目录读取文件 X"），而非泛化操作（"打开任意路径"）。

Wasm 反复出现在 agent 工具中的一个原因是 **component model** 方向：不是"这有个模块，调导出函数"，而是获得类型化接口和更好的组合。这推动你走向更小的工具、具有显式输入/输出——这恰好是你对能力范围化的 AI 工具所需要的。

另一面是你的宿主仍然需要小心。毁掉一个干净 Wasm 沙箱的最简单方式就是暴露一个过于强大的宿主函数。能力系统的失败模式是意外的环境权限。

实际考虑的约束：

- 线程存在，但各运行时和平台支持程度不同。
- WASI 网络一直在变化中（Preview 1 vs Preview 2；生态在追赶）。
- 动态语言通常需要解释器（Pyodide 等）。
- 任何期望"正常 Linux"的东西（shell、包管理器、任意二进制）都不能干净地移植。

主要运行时，供你评估：

- **Wasmtime**（Bytecode Alliance）：安全导向，紧跟 WASI/component-model 工作。
- **Wasmer**：运行时加工具链生态，WASIX 提供更 POSIX 化的 API。
- **WasmEdge**：面向边缘/云原生。

### V8 Isolates（以及默认拒绝运行时）

V8 isolates 是同一进程内 V8 JavaScript 引擎的隔离实例。Cloudflare Workers 等平台使用 isolates 以高密度、低启动开销运行大量租户。

隔离边界在于运行时：每个 isolate 有独立的堆和全局对象，通过受控方式共享或通信。

生产系统仍然在运行时进程外层叠加 OS 级防御作为纵深防御（命名空间/seccomp、代理进程做 I/O、针对时序侧信道的缓解措施）。运行时边界很强大，但如果你的威胁模型包括引擎逃逸，它不能替代 OS 隔离。

Deno 的权限模型是同一模式面向开发者的版本：V8 加上一个默认拒绝的能力模型（`--allow-read`、`--allow-net`、`--allow-run`）。

局限在于范围：isolates 只能用于 JS/TS（和嵌入的 Wasm）。如果你的沙箱需要任意 ELF 二进制，这不是合适的工具。

### 谁在 AI 中使用运行时沙箱？

反复出现的模式是 **Wasm 用于工具隔离**，而非"Wasm 作为整个开发环境"：

- [Microsoft Wassette](https://opensource.microsoft.com/blog/2025/08/06/introducing-wassette-webassembly-based-tools-for-ai-agents)：通过 MCP 运行 Wasm Components，具有默认拒绝的权限模型。
- [NVIDIA](https://developer.nvidia.com/blog/sandboxing-agentic-ai-workflows-with-webassembly/)：描述了使用 Pyodide（Wasm 中的 CPython）在浏览器沙箱中客户端运行 LLM 生成的 Python。
- [Extism](https://extism.org/)：一个 Wasm 插件框架，本质上就是"能力范围化的不可信代码执行"。

### 运行时沙箱何时够用

运行时沙箱适合特定场景：

| 约束 | 运行时沙箱的优势 |
|------|----------------|
| 无状态执行 | 出色 |
| 冷启动 / 密度 | 出色 |
| 完整 Linux 兼容性 | 否（仅限显式宿主 API） |
| 语言灵活性 | 有限（Wasm 语言 / JS） |
| GPU 访问 | 仅通过宿主提供的 API（如 WebGPU），非裸设备 |

如果产品需要完整用户空间和任意二进制，你最终还是会回到 microVM 或 gVisor。如果产品是"安全地运行小工具"，运行时沙箱可能是最干净的选择。

## 选择沙箱

大多数选型错误来自跳过边界问题直接进入实现细节。

以下是我实际的决策流程：

- **威胁模型：** 这段代码是可信的、半可信的还是恶意的？内核漏洞利用是否重要？
- **兼容性：** 你需要完整的 Linux 语义，还是可以在能力 API 内工作？
- **生命周期：** 你需要快速重置/快照，还是长期工作区？
- **运维：** 你能运行 KVM 和管理 guest 内核，还是受限于容器？

决策表：

| 工作负载 | 威胁模型 | 兼容性需求 | 推荐边界 |
|---------|---------|----------|---------|
| AI 编程 agent（多租户 SaaS） | 恶意（用户提交代码） | 完整 Linux、shell、包管理器 | microVM（Firecracker / cloud-hypervisor） |
| AI 编程 agent（单租户 / 自托管） | 半可信 | 完整 Linux | 加固容器或 gVisor |
| RL rollout（并行、大量重置） | 主要可信代码，需要每次运行隔离 | 快速重置、快照/恢复 | 支持快照的 microVM |
| 代码解释器（无状态代码片段） | 恶意 | 范围化能力，无 shell | gVisor 或运行时沙箱（如果语言适配） |
| 工具调用 / 插件 | 混合 | 显式能力面 | Wasm / Isolates |

两个常见的错误：

**错误 1："我们的代码是可信的。"** 在 agent 系统中，你运行的代码受不可信输入塑造（prompt 注入、依赖混淆、供应链攻击）。除非有充分理由，否则应将"半可信"作为默认假设。

**错误 2："我们把网络封掉就行了。"** 网络限制很重要，但它不是边界。如果你在共享内核上运行恶意代码，"无网络"沙箱仍然可以变成内核漏洞利用沙箱。

在选择边界之前，我还会写下一份**最小可行策略**。如果你无法执行这些，你还没有沙箱：

- **默认拒绝出站网络**，然后白名单。（或将所有流量路由通过策略代理。）
- **沙箱中无长期凭证。** 使用短期范围化令牌。
- **仅工作区文件系统**访问。除了你明确打算挂载的之外，无宿主挂载。
- **资源限制：** CPU、内存、磁盘、超时和 PID 数。
- **可观测性：** 记录进程树、网络出站和失败。没有遥测的沙箱就是事件响应的表演。

从零开始的具体默认选择：

- 多租户 AI agent 执行：**microVM**。Firecracker 提供密度和紧凑的 VMM 攻击面。cloud-hypervisor 如果你需要 VFIO/热插拔/GPU。
- "我已经在用 Kubernetes"：**gVisor** 是个不错的中间地带（如果兼容性可接受）。
- 可信/内部自动化：**加固容器**通常够用。
- 能力范围化工具：**Wasm 或 isolates**。

一条出奇好用的经验法则：

- 如果你需要 **shell + 包管理器**且不完全信任代码：从 **microVM** 开始。
- 如果你能接受**兼容性矩阵**以节省开销：考虑 **gVisor**。
- 如果你能将任务建模为**能力范围化的操作**：优先选择 **Wasm/isolate**。

然后用实测验证：冷启动、稳态吞吐量和运维复杂度。MicroVM 在规模化时可以很便宜，但前提是你的编排是为此而建的。

重点不是选出一个赢家。而是知道如果逃逸发生需要什么条件失败，并选择与该现实匹配的边界。

## 附录：本地操作系统沙箱

以上所有讨论都假设你在服务器上运行工作负载。本地 agent（Claude Code、Codex CLI 等）是不同的问题：

Agent 运行在你的笔记本上。它能看到你的文件系统。在这种情况下，失败模式通常不是"内核 0-day"，而是"prompt 注入诱骗 agent 读取 `~/.ssh` 或删除你的主目录"。

每个主流操作系统都有"轻量级、进程级"沙箱机制。这些仍然是共享内核边界内的策略执行，但它们被设计为用户可调用且快速。

![内核强制的沙箱策略图](../access/sandboxes-for-ai/seatbelt.webp)

### macOS Seatbelt（App Sandbox）

Seatbelt 是 macOS 的内核强制沙箱策略系统（SBPL 配置文件）。工具可以生成一个允许工作区和临时目录、拒绝 `~/.ssh` 等敏感路径的配置文件。当 agent 尝试访问时，内核返回 `EPERM`。Shell 无法"逃逸"内核检查。

关于工具的说明：`sandbox-exec` 多年前就被弃用了，但底层机制仍在 Apple 平台中广泛使用。现代工具倾向于通过 API/entitlements 应用沙箱，而非通过 CLI 包装器。

一个简单的 SBPL 示例：

```scheme
(version 1)
(deny default)
(allow file-read* (subpath "/Users/alice/dev/myrepo"))
(allow network-outbound (remote tcp "api.github.com:443"))
```

### Linux Landlock（+ seccomp）

Landlock 是一个无特权的 Linux Security Module，专为自我沙箱设计：进程可以限制自己的文件系统访问（在更新的内核上还有一些 TCP 操作），且限制是不可逆的并被子进程继承。

在大多数配置中，Landlock 与 seccomp 配合使用：Landlock 控制文件系统路径；seccomp 阻止高风险系统调用（`ptrace`、`mount` 等）。

在 API 层面，Landlock 就是几个系统调用：创建规则集 → 添加路径规则 → 强制执行。最小流程如下：

```c
int ruleset_fd = landlock_create_ruleset(&attr, sizeof(attr), 0);
landlock_add_rule(ruleset_fd, LANDLOCK_RULE_PATH_BENEATH, &rule, 0);
landlock_restrict_self(ruleset_fd, 0);
```

重要行为是限制是*单向的*（无法禁用）且被子进程继承。这使它适合"运行这个工具，但别让它碰其他东西"。

如果你想要一个实用工具入门，[landrun](https://github.com/Zouuup/landrun) 将 Landlock 包装成了 CLI。它需要 Linux 5.13+ 的文件系统规则和 6.7+ 的 TCP 绑定/连接限制。

### Windows AppContainer

AppContainer 是 Windows 基于能力的进程隔离（SID/令牌）。它被广泛用于浏览器渲染器隔离。AppContainer 进程使用受限令牌运行，只拥有你授予的能力（网络、文件系统位置等）。

对于编程 agent，它目前不太常见，主要因为设置相比"写个配置文件/应用一个规则集"更依赖 Win32 API。但如果你需要在 Windows 上强大的原生 OS 隔离而不启动 VM，它就是你要学的原语。

### 对比

| 方面 | macOS Seatbelt | Linux Landlock + seccomp | Windows AppContainer |
|------|---------------|------------------------|---------------------|
| 需要的权限 | 无 | 无 | 无（但设置是显式的） |
| 文件系统控制 | 配置文件规则 | 路径规则集 | 能力授权 |
| 网络控制 | 配置文件 + 代理模式 | 命名空间/seccomp（或有限的 Landlock） | 能力授权 |
| 不能解决什么 | 内核漏洞 | 内核漏洞 | 内核漏洞 |

所有本地沙箱都有一个运维陷阱：你必须允许足够多的权限让程序能运行。动态链接器、语言运行时、证书存储和临时目录都是"真实"的依赖。一个忘记了 `/usr/lib`（或 Windows 等价物）的默认拒绝沙箱会以令人困惑的方式失败。

**把配置文件当代码对待：** 版本化、测试、并预期它们会随着 agent 需求的变化而演进。

我个人只在启用沙箱的情况下运行我的代码 agent，也建议其他人这样做。
